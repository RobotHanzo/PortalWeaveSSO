# PortalWeave SSO implementation contract

An installable, dependency-free PHP 8.1+ WordPress 6.5+ plugin. Native Abilities need WordPress 6.9+ and the WordPress MCP Adapter for MCP transport. All functionality is bundled; add-ons are opt-in modules, not purchase gates.

## Module ownership and interfaces

All classes are in `PortalWeaveSSO`, use `ABSPATH` guards, and are loaded by the main plugin. Errors use `WP_Error` with stable `portalweave_sso_*` codes. Option name: `portalweave_sso_settings`. Network option has the same name; a network option with `network_enforced` true overrides site settings. App IDs are sanitized slugs and are stored as associative keys. No OAuth credentials or bearer tokens in logs, HTML, URLs (except required OIDC logout hints), or configuration support exports.

- `Config`: static `defaults()`, `app_defaults()`, `all()`, `get($key, $default = null)`, `apps()`, `app($id)`, `save(array $input, bool $network = false)`, `import(array $input, bool $network = false)`, `redacted()`, `callback(array $app = [])`. `all()` exposes decrypted secrets internally. Save merges secret placeholders/omissions with existing values. An empty secret clears it only with explicit clear control. Site saves cannot override enforced network policy. Import retains local credentials and disables incomplete providers/enforcement on clean restores.
- `Secrets`: static `encrypt($plaintext)`, `decrypt($ciphertext)` using authenticated encryption and WordPress salts.
- `Http`: static `json($url, array $args = [])` uses WordPress safe HTTP, HTTPS, no redirects, bounded body/time; returns decoded object-as-array or WP_Error.
- `Redirect`: static `validate($url, $fallback = '')` validates same-origin or explicit allowlist prefix with path boundary; `current()` returns current safe site URL.
- `ClientIp`: static `current()` resolves the current request's validated address for opt-in audit collection. Server-only `PORTALWEAVE_SSO_TRUSTED_PROXIES` and `PORTALWEAVE_SSO_CLIENT_IP_HEADER` define proxy/header trust; the default uses `REMOTE_ADDR` and ignores forwarded headers. Resolution is bounded, walks XFF from the nearest hop to the first untrusted address, and fails back to the connection address when the selected header or configuration is invalid. It does not mutate server globals or authentication policy. See [deployment settings](provider-setup.md#client-ips-behind-nginx-and-cloudflare).
- `Audit`: static `install()`, `record($status, $app = '', $user = null, $code = '', $navigation = '')`, `recent(array $args = [])`, `cleanup()`. Append-only transaction rows, weekly debug cleanup, bounded audit retention.
- `Jwt`: static `validate($jwt, array $app, array $context = [])` -> claims or WP_Error. Context: `nonce`, `access_token`, `require_at_hash`, `audience`, `issuer`. Explicit allowed algorithms, issuer/audience/expiry/iat/nonce, RSA JWKS, HMAC secret. No token-directed key URLs.
- `Auth`: static `register()`, `login_url($app_id, $redirect = '', $test = false, $popup = false)`, `logout_url($redirect = '')`, `refresh($user_id, $app_id)`, `token_meta_key($app_id)`, `app_meta_key()`, `remember_sid($user_id, $app, $attributes)`, `backchannel_logout($app_id, $token)`. Owns `portalweave_sso_action=login|callback|logout|logout_callback|password|backchannel_logout`, state/nonce/browser binding, token exchange and auth cookies. Calls `Accounts::resolve($app, $attributes, $tokens)`; `resolve` does not set cookies. Login tests are manage_options + nonce restricted and do not log the administrator in as the test subject. Provider array includes `id`.
- `Accounts`: static `resolve(array $app, array $attributes, array $tokens = [])` -> WP_User or WP_Error. Provider identity is issuer/app + immutable subject. Auto-link only on verified email and opt-in. Admin SSO disabled by default; verified per-provider admin claim required when enabled. Role, attribute, email/domain restrictions apply before mutations.
- `Admin`: static `register()`. Settings, provider forms, audit CSV, import/export, diagnostics, support, network administration, content restriction UI. Uses Config save and shared APIs.
- `Display`: static `register()`, `buttons(array $args = [])`; shortcode/widget/Woo/login screen, external assets only for scripts, logout placeholders.
- `Access`: static `register()`, `allows($rule, $user = null)`, `can_post($id, $user = null)`, `protect_media($id)`, `unprotect_media($id)`; site/content/category/attachment restrictions, standard login blocking, SSO enforcement. Private-media originals, derivatives and backup sizes are relocated outside the document root and URLs use authenticated delivery. Prior CDN copies and custom offloaded/image-regeneration integrations require deployment checks.
- `Extensions`: static `register()`. Opt-in SCIM, JWT SSO, guest identities, moderation, avatar mapping, attribute redirects, bounded shared-domain sign-in. Owns additional REST routes. Checks permissions and module toggles internally.
- `Abilities`: static `register()`. Exactly eight admin-only abilities; off by default; never exposes secrets. `Cli`: static `register()`.

App keys: `id`, `name`, `provider`, `enabled`, `protocol` (oidc/oauth2), `client_id`, `client_secret`, `scope`, `authorize_url`, `token_url`, `userinfo_url`, `groupinfo_url`, `jwks_url`, `issuer`, `logout_url`, `callback_url`, `credential_method` (header/body/none), `grant` (authorization_code/implicit/password), `legacy_grants` (false), `pkce` (true), `state_parameter` (custom value embedded in random state, never replaces it), `algorithms` (list; default RS256), `jwt_secret`, `subject_attribute` (sub), `mapping` (username,email,first_name,last_name,display_name,groups), `custom_mapping` (meta key => claim path), `role_mapping` (group => list of role slugs), `domain_roles` (domain => list), `default_role` (subscriber), `keep_roles`, `block_unmapped`, `auto_register`, `link_existing`, `keep_attributes`, `keep_email`, `allow_duplicate_emails`, `domain_mapping` (domain => domain), `allow_admin` (false), `verified_attribute` (email_verified), `verified_value` (true), `require_verified_email` (true), `icon_url`, `button_text`, `redirect_rules` (claim, equals, url), `guest`, `shared_sso`, `moderation`.

## Trust boundaries and acceptance evidence

Untrusted provider payloads cannot select keys/algorithms, override verified ID-token subject, map privileged WP meta, grant administrator implicitly, or redirect outside allowlists. State is short lived, one-use, browser bound, and bound to initiator redirect and provider. Network and site administration require their native capabilities and nonces. Tokens are encrypted at rest and never exported. On multisite, use Auth's metadata helpers and Accounts::groups_meta_key(); tokens, last-app, provider groups, SCIM state, moderation and avatars are scoped by blog ID. WordPress users and sessions remain global: any privileged site membership requires verified administrator policy before SSO. Media delivery and shared subdomains need an explicit deployment contract. Public browser login and privileged automation remain separate.

Verification includes PHP lint, focused cryptographic/security tests, a real WordPress integration environment where possible, and an installable ZIP. Live IdP and web-server deployment checks are documented as environment-dependent.

## Extension hooks

`portalweave_sso_pre_resolve` can supply a WP_User/WP_Error before normal account resolution; it has full authentication authority and must enforce equivalent policies. `portalweave_sso_account_allowed` runs before account changes. `portalweave_sso_user_resolved` observes the saved user and attributes. `portalweave_sso_pre_authenticate` can reject the resolved user before cookies. `portalweave_sso_authenticated` observes successful authentication. `portalweave_sso_login_redirect` supplies a destination that is still validated against the redirect allowlist. `portalweave_sso_audit_recorded`, `portalweave_sso_configuration_saved`, `portalweave_sso_cleanup_complete` and `portalweave_sso_backchannel_logout` expose operational events. `portalweave_sso_redacted_configuration` can adjust sanitized exports; do not reintroduce credentials.

Account resolution itself does not set auth cookies. Extension authors should not bypass the pre-authentication filter or redirect validation. Metadata starting with `_portalweave_sso_` is internal and must not be writable through custom claim mappings. Custom endpoint/content plugins must enforce Access::can_post themselves.
