# External services used by PortalWeave SSO

PortalWeave SSO runs in your WordPress installation. An administrator chooses and configures each identity provider before it can be used. Selecting a provider template fills local form fields; it does not register an account, contact that provider, or accept its terms for you. A new installation has no configured provider.

The plugin has no developer telemetry, advertising service, license-check server, or required plugin-vendor SaaS backend. Its JavaScript and stylesheets are bundled locally. It does not download executable code. WordPress's own update checks and services, other installed plugins, and the hosting platform are managed separately.

## Connections and information exchanged

| Feature and trigger | Destination and information exchanged |
| --- | --- |
| An SSO login or **Test SSO Config** starts | The browser visits the configured authorization endpoint. The request includes the registered client ID, callback URL, requested scopes, random state, and, where applicable, an OIDC nonce and PKCE challenge. The provider receives the browser's normal network information and may set its own cookies. Forced authentication or a single-flow policy can start this navigation automatically after an administrator enables it. |
| Authorization Code callback | WordPress sends the authorization code, callback URL and PKCE verifier, where enabled, to the configured HTTPS token endpoint. The configured client-authentication method sends the client ID and, for confidential clients, client secret in an HTTP Basic header or request body. Public PKCE clients can omit a secret. The provider returns tokens. |
| Profile or group lookup | WordPress sends the access token as a bearer credential to the configured user-info and optional group-info endpoints. Returned account identifiers, verified-email claims, profile fields and groups support account creation/linking, attribute mapping and access decisions. Scopes and mappings determine the information requested and retained. |
| Signed JWT validation | WordPress retrieves public signing keys from the configured HTTPS JWKS endpoint when needed, including when its local key cache expires or an allowed key rotation requires a refresh. This key request does not send the user's bearer token. HMAC validation uses the locally configured secret. |
| An explicit refresh operation | WordPress sends the stored refresh token and configured client authentication to the provider's token endpoint. The plugin does not run a background refresh service. |
| Explicitly enabled legacy Password grant | A user enters provider credentials in the plugin's password-grant form. WordPress submits those credentials to that provider's token endpoint over HTTPS. The plugin does not persist that password. Authorization Code with PKCE is the preferred flow. |
| Explicitly enabled legacy Implicit grant | The provider returns tokens to the browser callback; bundled local code relays the fragment response to WordPress for validation. This flow requires a signed OIDC ID token. |
| SSO logout | Where configured, the browser visits the provider's HTTPS end-session endpoint with the client ID, post-logout callback, random state and an ID-token hint when available. Signed OIDC back-channel logout is an incoming provider-to-WordPress request. |
| Optional SCIM provisioning | An administrator's provisioning service makes authenticated HTTPS requests to this site's SCIM endpoint. User and group payloads can create/update local accounts and return provisioning information to that client. The plugin does not choose an external provisioning vendor or poll one. |
| Optional shared-subdomain SSO | A short-lived signed cookie transfers selected mapped identity claims between explicitly trusted sites on the configured parent domain. It contains no OAuth access/refresh tokens. Participating sites can read its identity content; signing does not encrypt it. |
| Optional custom provider icon, WordPress sign-in button icon or mapped profile picture | A visitor's browser requests the administrator-selected or provider-supplied HTTPS image URL when it is rendered. A custom sign-in icon can load when the login page opens, before an authentication attempt; its Appearance preview also loads the selected image in the administrator's browser. The image host receives the visitor's IP address and ordinary browser request information. Sign-in button icons use `referrerpolicy="no-referrer"`; avatar requests follow the site's theme/browser policy. Bundled provider logos are served locally by the plugin. |
| An administrator submits support information | WordPress's configured mail service sends the message to the administrator-selected recipient. Configuration is attached only when requested in the form; the support ability prepares redacted configuration and sends only with an explicit `send=true` request. No support recipient is configured automatically. |

Outbound token, profile, group and JWKS requests use the WordPress HTTP API, HTTPS certificate verification and bounded responses. Authorization, logout, image and final allowed navigation URLs are browser requests. Administrators must verify every configured host; templates are starting points and can be edited.

The provider setup guide derives configuration locally and displays bundled provider artwork. It does not contact an identity service, image CDN or discovery URL while entering settings. Official documentation opens only when the administrator chooses its link. Bundled artwork attribution is recorded in `assets/providers/README.txt`; administrator-configured frontend icons and mapped pictures remain the separate remote-image flows described above.

**Test SSO Config** intentionally displays the provider's returned attributes to the authenticated administrator who initiated the test. It does not automatically send the result to support. Treat copied results and screenshots as personal data and remove secrets before sharing them.

## AI / MCP clients and other optional destinations

The eight abilities are off by default and require `manage_options`. MCP transport requires a separately installed/configured WordPress MCP Adapter. The plugin itself does not call an AI model, contact Claude/OpenAI/Cursor, or embed an AI SDK. An authenticated MCP client can request configuration details, diagnostics and personal audit data, and can request authorized changes or explicit support submission. Data returned through the adapter may then be processed by the chosen client or AI service. Select and disclose that client's actual policy and terms separately; enabling abilities does not select a client.

Booking, forum and demo/trial URLs are optional administrator-configured links. Opening one navigates to that destination; its operator's privacy notice and terms apply. Support mail delivery may involve the site's SMTP/email provider and recipient's systems. The plugin does not determine how those recipients retain messages.

Configuration redaction removes client identifiers, secrets and tokens from the structured configuration export. It cannot recognize every secret or personal detail an administrator types into a free-form support message or includes in a screenshot. Review that material before submitting it.

## Administrator disclosure and consent

Before enabling a provider, automatic login policy, image host, shared-domain handoff, provisioning client or MCP integration, explain the actual recipients, requested data, purposes and retention to affected users. Obtain any consent or organizational authorization your deployment requires. Provider consent screens and the plugin's technical switches do not decide the site's legal basis. Request only necessary scopes and mapped attributes, and review changes before expanding access. See [local data, cookies and erasure](privacy.md) for the WordPress-side behavior.
